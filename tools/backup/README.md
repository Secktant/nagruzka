# Бэкап всех зашифрованных снимков

Этот комплект устанавливается в Supabase и приватный `Secktant/nagruzka-backup`.
Он резервирует все строки `sync_blobs`, включая новые Sync ID, старые и тестовые
наборы. Отдельный токен разрешает только экспорт. Приложение продолжает работать
с прежними RPC, паролями и keyfile. Токен нужен только GitHub Actions.

## Подключение

1. В Supabase SQL Editor выполнить [setup.sql](setup.sql) от владельца БД.
2. Выполнить [rotate-token.sql](rotate-token.sql). Результат `backup_token`
   скопировать прямо в Settings → Secrets and variables → Actions приватного
   репозитория, в новый секрет `BACKUP_TOKEN`. Не сохранять значение в коде,
   сообщениях или скриншотах. Каждый повторный запуск этого SQL меняет токен.
3. Скопировать [backup.mjs](backup.mjs) в `nagruzka-backup/tools/backup.mjs`.
   Заменить прежний workflow содержимым [backup.yml](backup.yml) по его прежнему
   пути в `.github/workflows/`. Оставить один workflow с расписанием бэкапа.
4. Запустить Actions → backup → Run workflow. Проверить успешный экспорт,
   новый коммит и появление `backups/index.json` и `backups/snapshots/`.
   Секрет `SYNC_ID` новый workflow не использует.
5. Самостоятельно проверить восстановление нужного `.nz` на отдельном профиле
   приложения, сохранив перед этим свою актуальную зашифрованную копию.

В SQL Editor выводится секрет чтения всех шифроснимков. В таблице доступа
хранится его SHA-256. Повторное применение setup.sql сохраняет действующий токен.
Права SQL требуется проверить на целевой базе перед включением расписания.

## Файлы и восстановление

`backups/index.json` перечисляет снимки, присутствующие в текущей выгрузке,
их версии, время обновления и флаг `restorable` (пригодность упаковки в `.nz`). Для каждого хэша есть пара `.json` и `.nz` в
`backups/snapshots/`. Версии независимы между наборами. Выбирать копию следует
по известному времени изменения, затем проверять содержимое при восстановлении
в отдельном профиле. Хэш имени не раскрывает исходный Sync ID или адрес строки.

Формат `.nz` прежний — `NZENC1`, flags=1, соль, IV и шифротекст.
Он открывается паролем и keyfile исходного набора, если keyfile использовался.
Старые chunk-снимки до перехода на AAD `nagruzka:main` требуют также исходный
Sync ID в приложении. Это прежнее ограничение формата. Legacy без AAD читается
как раньше. Архив предназначен для импорта через приложение; исходные адреса
строк и таблица `sync_meta` в него не входят, полного дампа Supabase здесь нет.

Прежние `backups/latest.*` остаются исторической копией и больше не обновляются.
Удалённые на сервере строки сохраняются в файлах и git-истории. Автоматического
удаления копий нет. Повтор без изменений не создаёт коммит.

## Ошибки и отзыв доступа

Неверный токен, HTTP-ошибка, пустая выгрузка или нарушение структуры ответа
завершают запуск ошибкой. Проверяется весь ответ перед изменением файлов.
Строки с некорректным base64 или длиной соли/шифротекста сохраняются отдельно
в `backups/rejected/<хэш>.json` как исходные непроверенные поля сервера.
Возможность их расшифровки не подтверждена. В Actions появляется предупреждение с количеством,
в индексе у таких строк `restorable:false`. Их последние пригодные пары в
`snapshots/` сохраняются с прежней версией. Корректные строки продолжают
резервироваться. Старые файлы rejected тоже сохраняются; текущий статус задаёт
index.json. Пригодность формата не доказывает возможность расшифровки — это
проверяется владельцем с паролем и keyfile при репетиции восстановления.

Ошибка записи или push также завершает запуск ошибкой. При ошибке записи
часть файлов в одноразовом рабочем каталоге Actions может обновиться, но шаг
коммита не выполняется. Следующий запуск начинает с сохранённого коммита.

Для ротации снова выполнить rotate-token.sql и обновить BACKUP_TOKEN.
Для отзыва выполнить владельцем БД `delete from backup_private.access;`.
Это прекращает доступ через backup_export. Существующие копии остаются.

## Проверки комплекта

Из корня основного репозитория `node --test test/backup.test.js` проверяет
несколько ID, автоматическое добавление, сохранение исчезнувших наборов,
повторный запуск, ошибки и настоящую криптографию `.nz` трёх поколений.
SQL требует отдельной проверки на PostgreSQL с ролями Supabase. Локальные
Node-тесты не проверяют фактические права установленной серверной функции.

## Проверка совместимости архива

При изменениях упаковщика сравни tools/backup/backup.mjs с tools/backup.mjs
архива. В этой задаче проверено побайтовое совпадение с коммитом
0b336506735b09a04cc907da1e3b53e3d78daa50. При подготовке кандидата выполни
`npm run smoke:release` в корне приложения. Сценарий восстановления описан
в [регрессе QA](../../docs/QA.md). Личные копии для теста не нужны.
