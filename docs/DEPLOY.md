# Выпуск на GitHub Pages

1. «Разрабатывай» или равнозначное поручение разрешает реализацию, проверки, push фичевой ветки и публикацию кандидата. Начни от актуальной базы либо продолжи подходящую ветку. Зафиксируй критерии приёмки, пройди профильные проверки и [регресс QA](QA.md), укажи новый CACHE и SHA. Дождись независимого ревью коммита. Основной агент владеет Git, Actions и выпуском.
2. Push в main и PR запускают CI. Для любой ветки есть ручной запуск только проверок: `gh workflow run ci.yml --ref ВЕТКА -f mode=check`. Деплой требует явно выбрать `mode=publish` и допуск ветки в окружении github-pages. SSH-доступ к Git и авторизация gh проверяются отдельно. Проверь активную обкатку на общем адресе до публикации.
3. По первому поручению отправь проверенную ветку и запусти `gh workflow run ci.yml --ref ВЕТКА -f mode=publish`. Найди запуск этой ветки и SHA через `gh run list --workflow ci.yml --branch ВЕТКА`, дождись `gh run watch RUN_ID --exit-status`. Общая группа pages упорядочивает запуски публикации, но не резервирует адрес на всё время обкатки. При сбое выясни причину и заверши разрешённый этап. При повторной попытке запиши номер attempt.
4. Workflow готовит каталог сайта из index.html, style.css, manifest.webmanifest, sw.js, js/ и icons/. При новых корневых ресурсах обнови список упаковки. Проверяй версию, загрузку и изменённые ресурсы на https://secktant.github.io/nagruzka/ по содержимому опубликованных файлов. Передай ссылку, SHA, версию, run/attempt и короткие действия с ожидаемым результатом. Для реальных данных пользователь предварительно сохраняет .nz. Не замещай кандидата другой публикацией во время обкатки.
5. «Проверил, выпускай» относится к этому SHA, версии и запуску. Проверь состав PR, дождись проверок, выполни merge. Для новой версии кэша проверь точный diff и обновление установленной PWA. Любое изменение поведения требует нового кандидата и обкатки. После merge запусти `gh workflow run ci.yml --ref main -f mode=publish -f approved_run=RUN_ID -f approved_attempt=ATTEMPT`. Для публикации нужен манифест успешного деплоя одобренной попытки (срок хранения 90 дней). Если артефакт утрачен, опубликуй и согласуй нового кандидата.
6. Actions сверяет пути и SHA-256 всех подготовленных файлов, разрешая лишь изменение значения CACHE в копии sw.js из одобренного артефакта. При расхождении шаг деплоя не выполняется. После успеха сверь адрес, ресурсы, показанную версию и запуск приложения. Если публикация или проверка дала сбой, разбери причину до уборки.
7. Второе поручение разрешает уборку завершённой ветки. Сверь содержимое и итог PR (при squash сравни изменения, одной проверки родства SHA недостаточно), текущие tips локальной и удалённой веток, status и git worktree list. Удаляй только полностью вошедшую в релиз, свободную ветку без новых коммитов или несохранённой работы. При сомнении сохрани её и укажи причину. Передай PR, релизный SHA, запуск Actions, версию, адрес и судьбу ветки. Откат кода не восстанавливает данные.

**Пример прохождения.** Для изменения суммы рассрочки аналитик задаёт исходный график, финансист рассчитывает остаток, QA сверяет результат после оплаты и перезапуска. При зелёном регрессе и ревью кандидат A публикуется из ветки, пользователь проверяет сумму на телефоне и подтверждает A. После сверки манифеста выпускается main, проверяется сайт, свободная объединённая ветка удаляется. Если после перезапуска сумма неверна, QA фиксирует дефект и сценарий. В той же ветке появляется исправление B, проходит полный регресс и повторное ревью. Пользователь проверяет B по новой ссылке на запуск, подтверждение A на B не переносится.
