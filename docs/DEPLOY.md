# Публикация выбранной ветки

GitHub Pages использует GitHub Actions. `ci.yml` запускает проверки при push
в main, PR и ручном запуске. Только ручной `workflow_dispatch` после успешного
job `ci` публикует выбранную ветку. В обоих job checkout фиксируется SHA запуска.
Ручные публикации не выполняются одновременно: используется общая
concurrency-группа `pages`. Порядок запусков не гарантируется; новый запуск
может заменить ожидающий, поэтому во время обкатки другие выпуски не запускать.

Перед публикацией: повысить `CACHE` в `sw.js`, проверить состав коммита,
выполнить необходимые тесты, сохранить пользователем зашифрованный `.nz`.
В окружении `github-pages` должна быть разрешена выбранная ветка.

Команда для агента (после commit и push выбранной ветки):

```sh
gh workflow run ci.yml --ref feat/sync-reliability
gh run list --workflow ci.yml --branch feat/sync-reliability --event workflow_dispatch
gh run watch RUN_ID --exit-status
```

После успеха проверить опубликованные `sw.js` и номер версии на сайте.
Пользователь обкатывает фичевую версию по основному адресу
https://secktant.github.io/nagruzka/ — она доступна всем пользователям сайта.
Пока идёт обкатка, другие публикации не запускать. После подтверждения
«проверил, выпускай» оформить PR/merge, повысить версию и запустить этот же
workflow с `--ref main`. Сам merge в новой конфигурации выполняет только CI.

Существующий `ci.yml` уже зарегистрирован в main с `workflow_dispatch`, поэтому
можно запускать изменённый workflow из фичевой ветки до её merge. Старый workflow
в main пока ещё публикует main при push — до merge этой настройки такие push
во время обкатки выполнять нельзя. Возврат кода не восстанавливает данные.
