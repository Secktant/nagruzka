# Регресс кандидата

QA перед каждой обкаткой фиксирует SHA, CACHE, базовый релиз, среды и карту функций по текущим экранам, требованиям, тестам и прежним дефектам. Через основного агента получает примеры аналитика, независимый расчёт и сценарий отказа синхронизации. Для каждого кандидата выполняет все основные области. Для изменённых функций углубляет проверки.

| Сценарий | Исходные данные и действия | Что должно наблюдаться |
| --- | --- | --- |
| periods-money | Доходы 30 000 и 20 000, расход 6 000 в первом периоде. Проверить обе выплаты, даты до/на/после 15-го и конца месяца, февраль и смену года. Назначить банк. | Для первого периода нагрузка 20%, остаток дохода 24 000, по банку к оплате 6 000 до оплаты. Итоги сверить с ручным расчётом. |
| debt-calendar | Создать разовый платёж и рассрочку 9 000 со слотами 2 000 и 3 000 на одну дату и 4 000 на другую. Отредактировать, оплатить 2 000, открыть долги, периоды и историю, сохранить, удалить на отдельной копии. Проверить автоплан. | На первой дате изначально 5 000, после оплаты остаток долга 7 000. Сохранение сохраняет оставшийся слот, итог графика соответствует долгу. Проверить связи и историю удаления. |
| regular-history | Создать регулярный расход с прошлым и будущим вхождением, изменить сумму и отключить. | Прошлая сумма сохранена, будущие вхождения следуют новым правилам. |
| vault-reopen | Сохранить набор в IndexedDB, закрыть и открыть, включить замок с паролем и настроенным keyfile. Попробовать неверный пароль, отмену и верные данные. | При отказе исходные записи и ключ сохраняются. После успешного открытия даты, суммы и число записей совпадают. Биометрию проверить на целевом устройстве. |
| sync-two-devices | В двух изолированных профилях внести разные изменения, отключить сеть, перезапустить, вернуть связь. Отдельно прервать ответ после записи сервером, повторить запрос. | Обе конфликтующие копии доступны до выбора. После разрешения оба устройства сходятся. При повторе платежа его ID встречается ровно один раз на устройствах и сервере. |
| backup-restore | Синтетический зашифрованный снимок → рабочий упаковщик → импорт .nz в чистый профиль → повторное открытие. Проверить поддерживаемые прежние форматы, варианты пароля/keyfile, повреждение и отмену. | Сверить даты, записи, суммы и остаток с исходным набором. При отказе или отмене исходное состояние сохранено. |
| pwa-upgrade | На установленной прежней версии внести офлайн-платёж, подать новый сайт в тот же профиль, дождаться активации SW, открыть снова и вернуть связь. | Версия кандидата, даты и остаток верны, платёж один раз локально и после синхронизации. Проверить запуск из кэша без сети. |
| screens-mobile | В чистом профиле и на целевом телефоне пройти основные вкладки, историю, навигацию и формы, сохранить и отменить ввод. | Нужные элементы доступны, отмена сохраняет состояние. Открыта ожидаемая версия. |

Применяй все содержательные техники. Суммы и даты дели на классы эквивалентности и проверяй границы. Для форматов, пароля и keyfile составляй таблицу решений с последствиями. Для сети, замка и SW проходи переходы состояний, повторы и восстановление. Для браузеров, режима установки, сети и данных подбирай попарные сочетания и явно проверяй критичные комбинации. Связывай сценарии сквозными действиями от формы до сохранения и повторного открытия. Проверяй инварианты, обратимость экспорта и независимые суммы. Исследуй прошлые дефекты, отмену, повтор клика и прерывание операции. По условиям в изменённом коде проходи обе ветви и ошибки.

В корне проекта выполни `npm test`, `npm run check:assets`, `npm run smoke`, `npm run smoke:sync`, `npm run smoke:release`; общий запуск — `npm run ci`. Для дат повтори тесты с TZ=UTC и TZ=Europe/Samara. Для браузерных проверок нужны Playwright и Chromium (`npm install`, `npx playwright install chromium`). Локально допустим установленный Chrome с PLAYWRIGHT_CHANNEL=chrome. Используй изолированные профили, синтетические данные и тестовый RPC. Предыдущий подтверждённый SHA из main хранится в tools/confirmed-release.txt. При подготовке следующей ветки обнови его по проверенному релизу, обеспечь наличие объекта Git в клоне. Укажи исходный и итоговый SHA в отчёте. Автоматические сценарии дополни проверками оставшихся функций.

В отчёте укажи SHA, версию, команды и среды. Для каждой строки передай ревьюеру через основного агента: ID сценария, риск, технику, вход, действие, ожидаемый и фактический результат, статус (пройден, дефект, заблокирован, пропущен, после деплоя). При дефекте приложи шаги и свидетельство, добавь устойчивый сценарий или дополни существующий. Для iPhone дай конкретный шаг и ожидаемое поведение. Обязательная непроверенная область оставляет регресс неполным. Решение о риске пропуска или открытого дефекта принимает пользователь. При блокирующем дефекте исправь в той же ветке и повтори регресс и ревью нового кандидата.

Трассы браузерных падений сохраняются в Actions → запуск → Artifacts → traces-SHA-попытка на 14 дней. Распакуй скачанный артефакт и открой нужный файл командой `npx playwright show-trace <путь-к-trace.zip>`. Для контролируемой проверки вызови workflow с mode=trace-probe: boot-smoke должен упасть после переходов между вкладками и оставить открываемую трассу. Этот режим выполняет только проверки.

Если Trace Viewer сообщает, что трасса создана более новой версией Playwright,
используй версию из этого запуска CI: она видна в ключе шага «Кэш браузера Playwright».
Например, для `playwright-Linux-1.65.1` выполни
`npx --yes playwright@1.65.1 show-trace <путь-к-trace.zip>`.
Это позволяет открыть трассу без изменения зависимостей приложения.
Фактические результаты настройки четырёх проверок — в [отчёте](RELEASE-CHECKS.md).
