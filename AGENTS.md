# Работа над «Нагрузкой»

Личный платёжный календарь для 1–2 пользователей. Сохраняй простой стек:
vanilla JavaScript, ES-модули без сборки, IndexedDB, PWA и зашифрованные снимки
в Supabase. Предпочитай небольшие законченные изменения.

Актуальная редакция правил — **2026-11-25**. Два поручения пользователя и их
объём закреплены в разделе «Разработка, обкатка и выпуск» ниже.

## Контекст

- В начале каждого нового задания перечитай этот `AGENTS.md` с диска текущего
  Git-корня. Сверяй старые сводки чата с актуальными файлами; явные инструкции
  пользователя сохраняют приоритет.
- Этот каталог — Git-корень и корень сайта. Запускай Git, npm и Node здесь.
  Если рабочий каталог содержит `app/package.json`, сначала перейди в `app/`.
- В начале новой сессии прочитай `docs/CONTEXT.md`: текущее состояние, результаты
  предыдущей работы и следующий рекомендованный шаг. Затем читай README, код
  и тесты по задаче; полный аудит из `docs/audits/` открывай только по необходимости.
- В исходном рабочем каталоге может быть `../SPEC.md`: учитывай его согласованные
  правила, но сверяй сведения о версии и реализации с текущим кодом и CONTEXT.md.
  В отдельном клоне этого файла может не быть.
- Расчёты: `js/engine.js`, `js/autoplan.js`, `js/format.js`.
  Состояние и хранение: `js/store.js`, `js/db.js`.
  Синхронизация и защита: `js/sync.js`, `js/sync-ui.js`, `js/crypto.js`, `js/lock.js`.
  Интерфейс: `js/views/`. PWA и CI: `sw.js`, `tools/`, `.github/workflows/ci.yml`.
- Перед правками проверь Git status и сохрани чужие незавершённые изменения.
  Запрос на анализ означает анализ; внедряй исправления, когда это входит в задачу.
- Доступ к репозиториям настроен по SSH (подтверждено пользователем).
  Для Git-операций используй SSH-адреса, например `git@github.com:Secktant/nagruzka.git`.
  Ошибка HTTPS или отсутствие авторизации gh не означают отсутствия SSH-доступа.
  GitHub API и Actions требуют отдельной авторизации; SSH её не заменяет.
  Наличие доступа не является поручением на push, merge или деплой.
- Когда задача определена, переименуй текущий чат по её цели: например,
  «Синхронизация: сохранение офлайн» или «Рассрочки: исправление сумм».
  Используй доступный инструмент переименования чата; обновляй название только
  при существенном изменении задачи. Сохраняй название, явно заданное пользователем.
  Если инструмент недоступен, предложи название в ответе, не заявляя о переименовании.

## Основной агент и помощники

Основной агент выполняет роль maintainer: определяет критерий готовности,
меняет приложение, проверяет результаты помощников и собирает итог.
Определения проектных помощников находятся в `.codex/agents/`.
При каждом поручении передавай помощнику абсолютный путь Git-корня и требование
прочитать актуальные `AGENTS.md` и файл своей роли, даже если он уже работал
в этом чате. Не полагайся только на унаследованный текст прежней редакции.

Подключай `feature_analyst` перед реализацией новой фичи или неоднозначных
бизнес-правил: он изучает требования и код, предлагает варианты и готовит короткое
ТЗ. Основной агент проверяет его и уточняет существенные открытые вопросы
с пользователем. Для небольших однозначных исправлений аналитик необязателен.
Аналитик меняет только явно порученный документ в `docs/features/`; приложение
не редактирует. Уже согласованные требования не требуют повторного согласования.

Используй субагентов для следующих независимых проверок:

- `code_reviewer` — итоговое ревью коммита каждой завершённой задачи с изменениями:
  требования, корректность, регрессии, проверки и простота. Файлы не редактирует.
- `sync_security_reviewer` — при изменениях синхронизации, хранения, ключей,
  импорта/экспорта, блокировки или SQL. Проверяет код без редактирования.
- `finance_reviewer` — при изменениях сумм, дат, платежей, рассрочек,
  регулярных начислений и автоплана. Проверяет код без редактирования.
- `qa` — для воспроизведения существенного дефекта, независимой проверки
  исправления и сценариев с браузером, офлайном или перезапуском.
  Может менять только явно порученные тесты и фикстуры.

Небольшие правки текста и оформления выполняй самостоятельно; итоговое ревью
их коммита ограничивай документацией. Обычно подключай
одного профильного проверяющего; для рискованной задачи добавляй QA. Одновременно
используй не более двух помощников. Помощники не создают других субагентов.
Если механизм субагентов недоступен, выполни соответствующие проверки сам и укажи это.

В поручении укажи вопрос, критерий готовности, проверяемую версию/дифф и разрешённые
файлы. Проверяющие читают реальный код и связанные вызовы, а не только объяснение
автора. Не меняй проверяемые файлы во время проверки; после исправления замечания
передай обновлённый дифф. Два исполнителя не редактируют один файл одновременно.
Дождись результатов назначенных проверок перед заявлением о готовности.

## Правила данных и расчётов

- Не теряй неотправленные локальные изменения при получении серверного снимка,
  перезапуске, ошибке записи или конфликте версий. Ошибку нельзя выдавать за успех.
- Проверяй импорт до замены состояния; сохраняй возможность восстановить прежние
  данные. Строки из импортов и синхронизации считаются недоверенными для HTML.
- Проверка неверного пароля не должна менять рабочий ключ. Отключение синхронизации
  не должно снимать локальную защиту или оставлять фоновые отправки.
- Сохраняй совместимость существующих `.nz`, keyfile, AAD и форматов снимка.
  Изменение криптографии или формата требует проверки чтения прежних данных.
- Слоты плана рассрочки на одной дате суммируются; дата не является уникальным ID.
  Банк относится к рассрочке. Сохранение без изменений не должно удалять платежи.
- Перед изменением/отключением/удалением регулярного сохраняй его прошлые
  вхождения через `freezeRegular()`. Сумма 0 означает «не настроено».
- Разовый платёж: нет регулярного и рассрочки, сумма положительна.
  Согласованные правила меняются только в рамках поставленной пользователем задачи.

## Проверки

- Для исправления логики сначала воспроизведи ошибку небольшим тестом или
  исполняемым сценарием, затем убедись, что исправление устраняет её.
- `npm test` — юнит-тесты, Node >= 20; установка зависимостей не нужна.
  Для дат проверяй затронутые сценарии под `TZ=UTC` и `TZ=Europe/Samara`.
- `npm run check:assets` — список ресурсов service worker. Выполняй при изменении
  ресурсов, импортов и PWA; новый JS-модуль должен входить в `sw.js` ASSETS.
- `npm run smoke` — браузерная проверка запуска; требует Playwright и Chromium.
  Нужна при изменении модульного графа, интерфейса и старта приложения.
  Успешный boot-smoke не доказывает правильность расчётов и синхронизации.
- Проверяй синхронизацию с подменённой сетью и синтетическими данными; сохраняй
  настоящую криптографию в тестах её совместимости. Браузерные сценарии выполняй
  в изолированном профиле на локальном сервере. Не используй личный IndexedDB.
- Не проверяй запись, восстановление или смену ключей на боевом Supabase без
  прямого поручения. Не включай пароли, keyfile, Sync ID и личные копии в код и логи.
- Для изменений только инструкций/документации проверь синтаксис конфигурации,
  ссылки и diff; запуск приложения сам по себе не обязателен.

## Разработка, обкатка и выпуск

- Каждую завершённую задачу с изменениями заканчивай локальным проверенным
  коммитом. Анализ без изменений и незавершённая работа коммита не требуют.
  Объём разрешения для разработки и выпуска определяют два поручения ниже.
- После реализации, нужных проверок и обновления документации проверь состав
  diff и индекса; добавляй только файлы задачи. Чужие правки и staged-файлы
  не включай и не сбрасывай. Если безопасно отделить изменения нельзя, сообщи
  препятствие вместо коммита чужой работы. Не используй без разбора git add .
- Создай коммит-кандидат и передай `code_reviewer` base SHA, head SHA, требования
  или ТЗ, область задачи и результаты проверок. До его ответа не объявляй задачу
  готовой. Ревью относится к указанному SHA, а не к меняющемуся рабочему каталогу.
- Исправляй замечания отдельным коммитом, повторяй затронутые проверки и ревью
  нового HEAD. Не переписывай историю без поручения. P0/P1 и нарушения обязательных
  требований устрани до готовности; остальные замечания явно разбери в отчёте.
  Итоговое ревью не заменяет профильные проверки; сохраняй лимит двух помощников.
- В финальном ответе укажи итоговый SHA, результат ревью, проверки и ограничения.
  При недоступности субагентов выполни проверку сам и явно укажи отсутствие
  независимого ревью. Новые изменения после ревью требуют проверки нового SHA.
- Разрабатывай локально в фичевой ветке; создавай её до правок. Существующие
  незавершённые изменения сохраняй и не включай в выпуск без проверки состава.
- Поручение «разрабатывай» разрешает разработку в ветке, проверки, push ветки и
  деплой проверенного кандидата на основной Pages. Основной агент доводит этот
  этап до результата. Для задач только на анализ или настройку учитывай их границы.
- Перед каждой обкаткой QA отвечает за полный регресс кандидата по SHA и версии
  согласно [QA.md](docs/QA.md). Передавай разработчику, QA и ревьюеру единый
  пример приёмки, независимый расчёт и сценарии отказа от профильных ролей.
  Блокирующий дефект возвращает кандидата на исправление и повторную проверку.
- Передай пользователю URL, версию, SHA, run/attempt и сценарий приёмки.
  Сохраняй общий адрес за кандидатом до решения пользователя. Перед проверкой
  на реальных данных пользователь сохраняет зашифрованный экспорт.
- «Проверил, выпускай» разрешает PR/merge одобренной версии, публикацию main
  и уборку вошедшей в релиз свободной ветки после проверки сайта. Существенное
  изменение требует новой обкатки. Команды, сверка файлов и проверка безопасности
  удаления ветки описаны в [DEPLOY.md](docs/DEPLOY.md).

## Отчёт

После значимой завершённой работы обнови `docs/CONTEXT.md`: дату, фактический
результат, выполненные проверки, оставшиеся проблемы и следующий шаг. Держи
сводку примерно в пределах 60 строк; заменяй устаревшее, не веди дневник всех
действий. Подробности выноси в документы по теме со ссылкой из сводки.
Не сохраняй в ней секреты и личные финансовые данные. Не отмечай исправление
завершённым до проверки и не превращай рекомендованный шаг в разрешение на работу.

Пиши по-русски. Кратко укажи результат, изменённые файлы, выполненные проверки
и ограничения. Для дефекта дай приоритет, ссылку на код, условия воспроизведения
и последствие. Отделяй подтверждённое поведение от предположений. Не называй
проверку пройденной, если она не запускалась или недоступна.

Инструкция «не редактировать» задаёт поведение роли; технические права помощников
наследуются от основного сеанса. Примеры использования: `docs/CODEX.md`.
